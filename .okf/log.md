## 2026-09-27
* **Fix**: EXEC keyword overrides on an `EXEC procname` statement now reach the procedure's steps (new `explosion.apply_exec_parameter_overrides`). `PARM.procstep=`, `COND.procstep=`, `REGION.procstep=` and the unqualified forms (`PARM=` → first step, nullifying PARM on the rest; other keywords → every step) were tokenized onto the EXEC step and then dropped during explosion, so `EXEC P,PARM.B='NEWB'` left step B running with the PROC's own PARM and `COND.B=(8,LT)` never reached RC analysis. `KEY=` nullifies; an override naming no procstep warns. This was the documented "known limitation" in [advanced/proc-expansion](advanced/proc-expansion.md#exec-parameter-overrides). Regression tests: `tests/unit/test_exec_parameter_overrides.py`.
* **Fix**: PROC DD overrides now *merge* into the overridden DD instead of replacing it (`explosion._merge_dd_override`, used by both `apply_dd_overrides` and `apply_unqualified_dd_overrides`). Per z/OS an overriding DD changes only the parameters it codes, and `KEY=` nullifies one; both paths swapped in the override DD wholesale, so `//PS.D1 DD DSN=OVR.DATA` over `//D1 DD DSN=&X..DATA,DISP=SHR,UNIT=SYSDA` exploded with `disposition=None` and no `UNIT` — the dataset read as having no stated disposition in every downstream inventory. Mutually exclusive data-source parameters (`DSN`/`DSNAME`/`SYSOUT`/`PATH`/`DUMMY`/`*`/`DATA`) displace each other; an in-stream override still replaces the DD. See [advanced/proc-expansion](advanced/proc-expansion.md#dd-overrides). Regression tests: `tests/unit/test_dd_override_merge.py`.
* **Fix**: `program_profiles/_invoked.extract_invoked_programs` (the program behind an `IKJEFT01` / DSN wrapper) now reads SYSTSIN the way TSO does. It missed `RUN PROG(X)` (TSO keyword abbreviation; `PROGR`/`PROGRA` too), `RUN -` continued onto the next line (`-`/`+` continuation), `PROGRAM('X')` (quoted name) and `RUN PLAN(P) PROGRAM(X)` (operands in any order), and it reported programs inside a `/* ... */` TSO comment as real. New `_normalize_control_text()` strips comments (to `*/` or end of line) and joins continuations before matching. The backend's mirror (`src/parsers/jcl/inline_program_extractor.py`) gets the same change. Regression tests: `tests/unit/test_invoked_programs.py::TestTsoControlTextForms`.

## 2026-09-26
* **Fix**: a symbol whose *value* references other symbols now resolves through them. `explosion._make_replacer` re-substitutes a value containing `&` (bounded by `_MAX_NESTED_SUBSTITUTION = 8`, which also stops cycles), leaving a still-undefined reference as written; and a value that ends in a bare `&NAME` gets a delimiting period so it cannot swallow the next character. Before, `EXEC MYPROC,HLQ=&SYSUID` / `PROC HLQ=&SYSUID` + `DSN=&HLQ..IN` exploded to `&SYSUID.IN` (never resolved, separator eaten) instead of `TESTUSER.IN`, and `SET HLQ=&SYSUID` was dropped from the SET scope as "unresolved" so `&HLQ..DATA` was blanked to `.DATA`. `_has_unresolved_symbol_ref()` takes an `ignore=` predicate; the SET pass ignores system symbols there. Regression tests: `tests/unit/test_system_symbols_set_pass.py::TestSymbolValuesThatAreSystemSymbols`, plus `TestDsnameInContext` in `test_dd_dsname_alias.py`.
* **Fix**: `_post_parse.resolve_set_symbols` no longer blanks z/OS system symbols. With any `// SET` in the job it elided every symbol no SET defined, `&SYSUID` included, so `DSN=&SYSUID..WORK.DATA` became `.WORK.DATA` before `explode_job()` could resolve it from its `SystemSymbolProvider`. New `system_symbols.is_system_symbol_name()` (reserved `SYS` prefix + the JES dynamic date/time/job symbols) is passed as the new `keep_undefined=` predicate of `substitute_symbols` / `substitute_parameters_dict` / `substitute_dd_statement`, which leaves an undefined symbol it accepts as written. Other undefined symbols are still elided with a warning (pinned by `test_bug_fixes.py::TestSetSymbolSubstitution::test_undefined_symbol_left_as_is`). Regression tests: `tests/unit/test_system_symbols_set_pass.py`.
* **Fix**: `_model_factories._create_dd_from_statement` now reads `DSNAME=` (the long form of `DSN=`) into `DDStatement.dataset_name` when no `DSN=` is coded. Only `DSN` was read, so `//DD1 DD DSNAME=A.B` had `dataset_name=None` and the dataset vanished from every inventory and from PROC explosion's symbol substitution. The CLI `steps` DD listing also stops echoing `DSNAME` as an extra parameter. Regression tests: `tests/unit/test_dd_dsname_alias.py`.

## 2026-09-20
* **Fix**: the copy/compare/update utility profiles (`program_profiles/iebgener.py` — IEBGENER/IEBCOPY/ICEGENER, `iebcompr.py`, `iebupdte.py`) now derive each `DatasetEvent`'s `action` and `disp_status` from the DISP the DD actually states, via the new shared `base._dd_event()` helper, instead of hardcoding one per DD *role*. SYSUT1 was always reported `OPEN_SHARED` and SYSUT2 always `ALLOCATE`/`disp_status="NEW"`, whatever the JCL said — so `//SYSUT2 DD DSN=OUT,DISP=MOD` (an append, and how IEBUPDTE updates a source library in place) came back as a fresh allocation, and `//SYSUT1 DD DSN=IN,DISP=OLD` came back as a shared open while carrying `disp_status="OLD"`, an event contradicting itself. ## 2026-07-24
* **Fix (audit)**: Follow-up completeness audit of the parser (post god-class-split, PR #34/#35) targeting silent data loss — same charter as the earlier `jcl-parse-audit` branches. Verified the god-class split itself didn't drop any statement-type handling (it didn't), then found and closed 6 further gaps, all with regression tests in `tests/unit/test_silent_drop_fixes.py`:
  1. `SCHEDULE` was in `_statement_parser._STATEMENT_TYPES` since the parser's first commit but had no branch in `JobBuilder.handle_statement` — silently dropped with zero trace, not even the deliberate `pass` NULL/COMMAND/CNTL/ENDCNTL get. Added an explicit no-op branch alongside them.
  2. `continuation_handler.JCL_KEYWORDS` was an independently-maintained copy of `_STATEMENT_TYPES` that had drifted, missing `EXPORT`/`COMMAND`/`SCHEDULE`/`XMIT`/`THEN`/`NULL` — a nameless statement of one of these types, indented after a complete previous statement, was misclassified as a continuation and merged into the previous statement's last field, corrupting it and silently discarding the new statement. `JCL_KEYWORDS` is now derived from `_STATEMENT_TYPES` (`JCL_KEYWORDS = _STATEMENT_TYPES | {"GOTO", "SCHED"}`) so the two can't drift again.
  3. `ParameterParser._split_parameters` dropped empty comma-separated segments unconditionally (leading/internal/trailing), unlike its sibling `_parse_list_parameter` which already preserved internal empties for `DISP=(,CATLG,DELETE)`-style omitted subfields. An omitted leading positional (`JOB ,'PROGRAMMER',CLASS=A`) shifted every later positional down one index. Now only trailing empties (from a trailing comma) are stripped.
  4. `_create_job_from_statement` stripped *every* positional parameter key from `job.parameters`, not just the one (`_pos_0`) it consumed into `accounting_info` — silently discarding the JOB statement's second positional (programmer-name) operand. Now mirrors `_create_step_from_statement`: pops only `_pos_0`, leaves the rest in `job.parameters`.
  5. `explode_job()` rebuilds a new `Job` from the parsed one; the metadata-copy loop forwarded `unresolved_output_refs`/`sql_detections`/`jes_statements`/etc but not `warnings` — every diagnostic recorded during `parse_jcl()` vanished the moment a caller ran the documented `parse_jcl()` → `explode_job()` workflow. `warnings` added to the copy loop.
  6. Qualified `PROCSTEP.DDNAME` overrides (`apply_dd_overrides`) only ever replaced a same-named DD; if none existed on the target step the override was silently discarded, unlike the unqualified path (`apply_unqualified_dd_overrides`, fixed 2026-06-28) which already appends. Now appends when no match is found, and normalizes the resulting `DDStatement.name` to the plain DD name instead of the raw qualified key (a second bug hit while fixing the first — affected the replace path too).
  7. (Stretch) Undefined `&SYMBOL` references resolved *during* PROC expansion (against PROC defaults/EXEC overrides/system symbols — a code path `parse_jcl()` never reaches, since it doesn't expand PROCs) never warned, because no caller inside `explosion.py` passed `warnings=` to `substitute_symbols`/`substitute_parameters_dict`/`substitute_dd_statement` despite all three already supporting it. Threaded a shared `warnings` list through `_explode_step`/`expand_proc_invocation`/`explode_job`'s `_process_steps`, merged into `exploded_job.warnings` alongside fix 5's forwarded warnings.

  Two items investigated and explicitly left as documented limitations (not fixed — see [development/invariants](development/invariants.md) #16): a nameless, indented statement whose keyword this parser doesn't recognize at all is inherently ambiguous between "continuation" and "new unknown statement" given the heuristic (non-column-based) approach — fixing gaps 1–2 above closes this for every keyword the parser *does* support, but a genuinely unknown keyword still needs real column-field parsing to resolve reliably. And `PARM.procstep=value` (a per-step `PARM` override on `EXEC PROC=`) is tokenized but has no implementation anywhere in explosion — not a regression, just a feature that was never built (see [advanced/proc-expansion](advanced/proc-expansion.md)).

  One item investigated and rejected as out of scope: `DISPValidator`/`DatasetNameValidator` compute advisory `.warnings` (e.g. "consider CATLG or KEEP", "consider multi-level names") that the `validators.py` compatibility wrappers never surface — but these fire on fully *valid* JCL where nothing is lost, and `job.warnings == []` is an asserted contract for valid input throughout `test_silent_drop_fixes.py`; wiring lint-style advisories into it would spam every clean job and belongs in the `lint/` subsystem instead.

  Also corrected [development/invariants](development/invariants.md) invariant #8, which was stale: there is no `job.statements` field and comments are never preserved as `Statement(type="COMMENT")` — that never matched the current model (comments are dropped, with one JES3-`/*ROUTE XEQ` exception). Updated [advanced/proc-expansion](advanced/proc-expansion.md) (DD override table, symbol-substitution warnings) and [development/invariants](development/invariants.md) (added #15 dispatch-completeness invariant, #16 known limitation, corrected #8). Full suite: 2080 passed / 2 skipped, coverage 95.02%.

The parser stores unqualified overrides on the EXEC step's own `dd_statements` (only dotted `PROCSTEP.DDNAME` overrides went to `dd_overrides`), and `_explode_step` previously ignored them — so an *added* override like `//LOANRPT DD …` on `EXEC PROC=IMSBTCH` vanished during explosion. New `apply_unqualified_dd_overrides()` replaces a same-named proc DD or appends a new one (z/OS semantics). Tests: `tests/unit/test_explosion.py::TestDDOverrides` (added vs replaced). Updated [advanced/proc-expansion](advanced/proc-expansion.md) §DD Overrides. (Motivated by the backend IMS-BMP dataset-resolution fix — see backend `.okf/log.md`.)
